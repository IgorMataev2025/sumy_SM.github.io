# Портал послуг Safina — вихідний код (Web Forms)

Застосунок ASP.NET Web Forms (VB.NET, .NET Framework 4.8) з MySQL —
**усі 6 етапів з `ТЗ_портал_послуг.md` (розділ 9) реалізовано**:
інфраструктура, підключення до БД, реєстрація/авторизація, оголошення
постачальника, адмін-модерація, каталог і пошук для споживача. MVP
повний. Модель проєкту — **Website Project** (без `.vbproj`): ASP.NET
компілює сторінки на льоту, спеціальний білд-крок не потрібен — досить
скопіювати цю папку на сервер з IIS.

## Що вже є

- `Web.config` — цільовий фреймворк 4.8, Forms-автентифікація, портал
  закритий (`deny users="?"`) окрім `Login.aspx`, `Register.aspx`,
  `RegisterConsumer.aspx`, `RegisterProvider.aspx`, `Donate.aspx`,
  `DonationCallback.aspx`, `DonationResult.aspx`, `css/`, `js/`. Рядок
  підключення винесено через `configSource` у `ConnectionStrings.config`
  (поза git — див. розділ «Секрети» нижче).
- `Site.master` — спільний layout (шапка, навігація, підвал).
- `Default.aspx` — головна сторінка зі списком категорій, які **реально
  читаються з MySQL** (`App_Code/ServiceCategory.vb` → `DbHelper.vb`,
  параметризовані запити). При недоступній БД показує повідомлення
  замість 500-ї помилки.
- **Реєстрація/вхід (етап 2, ТЗ п.4.1):**
  - `Register.aspx` — тільки розвилка вибору типу акаунта (дві картки),
    сама реєстрація відбувається на окремих сторінках нижче (Постачальник
    і Споживач розведено за уточненою постановкою від 2026-09-07 —
    раніше був один спільний Register.aspx з перемиканням через
    `rblUserType`).
  - `RegisterConsumer.aspx` — email/пароль, ПІБ, телефон, район (вільний
    текст — повний довідник районів/громад ще не визначено, ТЗ розділ 10).
  - `RegisterProvider.aspx` — ті самі поля + фіз./юр. особа (назва
    компанії + ЄДРПОУ, 8 цифр), умовне поле показується через
    AutoPostBack (`chkLegalEntity`).
  - `Login.aspx` — email+пароль, повідомляє окремо про хибний
    пароль/заблокований акаунт/непідтверджений email.
  - `Logout.aspx` — вихід (`FormsAuthentication.SignOut`).
  - `ConfirmEmail.aspx` — підтвердження email за токеном із посилання.
  - `ForgotPassword.aspx` / `ResetPassword.aspx` — відновлення пароля за
    токеном (дійсний 1 годину); однакове повідомлення незалежно від того,
    чи існує email, — форма не дає перевірити зареєстровані адреси.
  - `App_Code/PasswordHasher.vb` — PBKDF2-SHA256, 100 000 ітерацій, сіль
    16 байт, версіонований формат рядка; порівняння за постійний час.
  - `App_Code/UserAccount.vb` — реєстрація/логін/токени, лише
    параметризовані запити (ТЗ, розділ 8).
  - **Email не надсилається насправді** — SMTP на хостингу ще не
    підключено. Посилання підтвердження/скидання пароля показуються
    прямо на сторінці (dev-режим, свідоме рішення на цьому етапі).
  - `Site.master` показує email користувача + «Вихід», коли він увійшов,
    інакше — «Вхід»/«Реєстрація».
- `Global.asax` — точка входу застосунку.
- `App_Data/schema.sql` — DDL-скрипт повної схеми БД (ТЗ, розділ 7 +
  `Description` в `Categories` і поля підтвердження email/скидання
  пароля в `Users`, додано понад ТЗ) з початковим наповненням
  4 MVP-категорій.
- `App_Data/migration_002_auth.sql` — окрема міграція для полів етапу 2
  (застосована до dev-БД; на новому розгортанні досить `schema.sql`).
- `bin/MySql.Data.dll` — MySQL Connector/NET 26.7.0 (.NET Framework 4.6.2,
  без зовнішніх залежностей). Комітиться свідомо: Website Project без
  NuGet-restore, інакше після `git clone` сайт не збереться.

- **Оголошення постачальника (етап 3, ТЗ п.4.2):**
  - `MyServices.aspx` — особистий кабінет: список власних оголошень зі
    статусами (Чернетка/На модерації/Опубліковано/Відхилено), кнопки
    «Подати на модерацію» і «Зняти з публікації» (`OnItemCommand` у
    Repeater). Доступний лише для `UserType = Provider`.
  - `ServiceEdit.aspx` — створення/редагування: категорія (з БД), назва,
    опис, ціна, район, телефон, до 5 фото (jpg/png/gif, ≤3 МБ кожне,
    `asp:FileUpload AllowMultiple="true"`). Редагування дозволене лише
    поки статус Чернетка/Відхилено — під час/після модерації сторінка
    показує заблоковане повідомлення замість форми.
  - `App_Code/Service.vb` — CRUD + переходи статусів, лише параметризовані
    запити. `App_Code/ServicePhoto.vb` — модель фото.
    `App_Code/ProviderPageBase.vb` — базовий клас сторінок постачальника
    (перевірка ролі, інакше редірект на `Default.aspx`).
  - Фото зберігаються у `Uploads/Services/{ServiceId}/` (поза
    `App_Data/` — той блокується ASP.NET для прямих HTTP-запитів, тому
    зображення там не показати). Папка не в git (тільки `.gitkeep`) —
    вміст користувацький. **App Pool-у потрібні права на запис** у
    `Uploads/` (див. розділ dev-середовища нижче).
  - `Site.master` показує пункт «Мої оголошення» тільки постачальникам.

- **Адмін-панель / модерація (етап 4, ТЗ п.4.3):**
  - Роль адміністратора — окремий прапорець `Users.IsAdmin`
    (`migration_003_admin.sql`), **не** значення `UserType`: форма
    реєстрації admin-а не пропонує, це власник порталу, якому власник
    хостингу вручну виставляє прапорець у БД (`UPDATE Users SET
    IsAdmin = TRUE WHERE Email = '...'`).
  - `AdminModeration.aspx` — черга «на модерації» (FIFO, найстаріші
    спершу), кожен рядок з даними постачальника; «Схвалити» або
    «Відхилити» з обов'язковим коментарем — причина одразу видима
    постачальнику в `MyServices.aspx` (поле вже існувало з етапу 3).
    Кожна дія пишеться в `ModerationLog`.
  - `AdminCategories.aspx` — додати / редагувати / деактивувати
    категорію; деактивована відразу зникає зі списку в `Default.aspx`
    і випадаючого списку `ServiceEdit.aspx` (обидва фільтрують
    `IsActive = 1`), але лишається в БД (`Services.CategoryId`
    посилання не ламаються).
  - `AdminUsers.aspx` — таблиця всіх користувачів, «Заблокувати» /
    «Розблокувати» (перемикає вже наявний `Users.IsActive` — той самий
    прапорець, який `Login.aspx` перевіряє з етапу 2, тому блокування
    одразу забороняє вхід). Адміністраторів заблокувати не можна —
    захист і в розмітці (кнопка прихована), і на рівні SQL
    (`AND IsAdmin = FALSE` у `UserAccount.SetActive`).
  - `App_Code/AdminPageBase.vb` — базовий клас сторінок адмінки
    (перевірка `IsAdmin`, інакше редірект на `Default.aspx`).
  - `Site.master` показує пункти «Модерація» / «Категорії» /
    «Користувачі» тільки адміністраторам.

- **Каталог і пошук (етап 5, ТЗ п.4.4):**
  - `Catalog.aspx` — доступний будь-якому автентифікованому користувачу

    оголошення). Фільтри: категорія, район (список формується
    динамічно з районів, де вже є опубліковані оголошення — повний
    офіційний довідник районів/громад лишається відкритим питанням

    ціна від/до. Пагінація — 12 карток на сторінку.
    Перехід з картки категорії на `Default.aspx` одразу відкриває
    каталог із застосованим фільтром (`Catalog.aspx?categoryId=X`).
  - `ServiceDetails.aspx` — повна картка: опис, усі фото, контакти
    постачальника (ПІБ, телефон). Показує лише опубліковані

    оголошення на модерації дає «не знайдено», не витік даних.
  - `App_Code/Service.vb` — `SearchApproved` (параметризований

- **Юридичний модуль — договір по оголошенню (уточнена постановка від
  2026-09-07, п.3):**
  - `ServiceContract.aspx` — динамічно генерує «Договір про надання
    послуг» для конкретного оголошення (`?id=ServiceId`), підставляючи
    дані Виконавця (постачальник, з БД) і Замовника (поточний
    користувач). Доступний будь-якому автентифікованому користувачу,
    крім власника самого оголошення (для нього — пояснювальне
    повідомлення замість договору; посилання на `ServiceDetails.aspx`
    теж ховається для власника).
  - Шаблон спирається на загальні положення глави 63 Цивільного
    кодексу України (ст. 901–907: предмет, оплата, відповідальність) і
    Закон «Про захист прав споживачів» — це типовий каркас, а не
    індивідуальна юридична консультація; застереження про це показане
    і на сторінці (поза друком), і в самому тексті договору (в друку).
  - Паспортні дані/РНОКПП/адреса реєстрації/банківські реквізити НЕ
    збираються при реєстрації — у надрукованому договорі це поля для
    заповнення власноруч перед підписанням.
  - Друк — через `window.print()` (кнопка, `UseSubmitBehavior="false"`,
    без постбеку); `@media print` у `css/site.css` ховає шапку/футер/
    навігацію (`.no-print`), лишаючи тільки сам документ.
  - `App_Code/UserAccount.vb`: додано `GetById(userId)` — потрібен,
    щоб дістати дані постачальника окремо від поточного залогіненого
    користувача.
  - Усі підставлювані користувацькі дані (ПІБ, назва компанії, опис
    послуги тощо) проходять через `Server.HtmlEncode` — на відміну від
    інших `asp:Literal` на сайті (напр. `descriptionLiteral` у
    `ServiceDetails.aspx`), які виводять текст без екранування
    (`Literal` за замовчуванням `Mode="PassThrough"`, не автоекранує).
    Це не нова вразливість цієї сторінки, але вартий уваги наявний
    момент в іншому місці сайту — не виправлялося в межах цього кроку.
  - Перевірено живим end-to-end тестуванням: реєстрація Постачальника
    (юрособа) і Споживача → оголошення → пряме схвалення в БД → договір
    з боку Споживача (коректні блоки Виконавця/Замовника, кирилиця,
    ціна) → та сама сторінка з боку власника (показує пояснення,
    не документ) → неіснуюче/невалідне `id` (коректне «не знайдено»).

- **Донат-модуль — підтримка проєкту через LiqPay (уточнена постановка
  від 2026-09-07, п.1):**
  - `Donate.aspx` — публічна сторінка (доступна без входу — підтримати
    проєкт може будь-хто): сума (пресети 50/100/300/500 грн або своя),
    необов'язкові ім'я/email. По кліку створює запис `Donations` зі
    статусом `Pending` і POST-ить напряму на
    `https://www.liqpay.ua/api/3/checkout` — в обхід серверної
    `<form runat="server">` зі `Site.master` (HTML не дозволяє вкладені
    форми, а ця веде на зовнішній домен): код-бехайнд пише власну
    мінімальну HTML-відповідь через `Response.Write`/`Response.End()`.
  - `App_Code/LiqPayHelper.vb` — підпис/перевірка за офіційним
    алгоритмом LiqPay checkout API v3: `signature =
    base64(sha1(private_key + base64(json) + private_key))`. JSON
    запиту/відповіді збирається/розбирається вручну (`String`/`Regex`)
    — без зовнішньої бібліотеки (Website Project без NuGet-restore).
  - `DonationCallback.aspx` — `server_url`, сюди LiqPay шле
    server-to-server POST одразу після обробки платежу; підпис
    **обов'язково** перевіряється тут (`LiqPayHelper.VerifySignature`,
    порівняння за постійний час) — саме цей файл робить статус донату
    остаточним у БД. Публічний, без входу.
  - `DonationResult.aspx` — `result_url`, сюди повертається браузер
    користувача (`?order_id=...`). Лише інформаційне повідомлення
    (Success/Pending/Failure/не знайдено) за вже записаним у БД
    статусом — цій сторінці, на відміну від callback, не довіряємо
    (її може відкрити хто завгодно з довільним `order_id`).
  - `App_Code/Donation.vb` — модель + `Create`/`GetByOrderId`/
    `UpdateStatus`, лише параметризовані запити.
    `App_Data/migration_004_donations.sql` — таблиця `Donations`
    (застосована до dev-БД; включена і в `schema.sql`).
  - Ключі LiqPay — `Web.config`, `<appSettings file="LiqPay.config">`
    (той самий домердж-прийом, що `configSource` для
    `connectionStrings`, тільки в appSettings це робить атрибут `file`,
    а не повна заміна). `LiqPay.config` — поза git (`.gitignore`),
    `LiqPay.config.example` — шаблон, комітиться.
  - Пункт навігації «Підтримати проєкт» у `Site.master` — видимий
    завжди, і анонімним відвідувачам, і залогіненим (поза
    `anonNav`/`userNav`).
  - **Грабля (та сама природа, що вже описана вище):** `SHA1.Create()`
    у `Using` без явного типу — `BC30980: Type of 'sha1' cannot be
    inferred` (перевантаження `SHA1.Create`/`HashAlgorithm.Create`
    плутають висновування типу VB). Виправлено `Using sha1 As SHA1 =
    SHA1.Create()`. І ще раз регістронезалежність VB.NET: `Dim
    donation = Donation.GetByOrderId(...)` конфліктувало з класом
    `Donation` — перейменовано на `record`.
  - Перевірено живим end-to-end тестуванням (з placeholder-ключами
    `sandbox_XXXXXXXXXXXX` — реальний LiqPay кабінет користувач
    підключить сам): анонімний GET `Donate.aspx` → сабміт форми →
    коректний base64 JSON і підпис у формі редиректу → запис `Pending`
    у БД → підписаний callback (сформований тим самим алгоритмом і тим
    самим ключем — імітує LiqPay) переводить у `Success` з
    `PaymentId`/`LiqPayStatus` → callback з невірним підписом
    відхиляється (400), запис не змінюється → `DonationResult.aspx`
    коректно показує Success/Pending/Failure/не знайдено.
  - **Не перевірено і не могло бути перевірено локально:** сам факт
    реального переказу грошей через LiqPay — для цього потрібен
    публічно доступний сервер (LiqPay не достукається до localhost) і
    реальна картка. Коли будете готові — можна протестувати на
    бойовому хостингу SmarterASP.NET мінімальною сумою.

- **Політика конфіденційності (уточнена постановка від 2026-09-08,
  п.4 — закриває відкрите питання ТЗ, розділ 10, «Політика обробки
  персональних даних»):**
  - `PrivacyPolicy.aspx` — публічна статична сторінка (без входу,
    `<location>` у `Web.config`), 10 розділів за Законом України «Про
    захист персональних даних» від 01.06.2010 № 2297-VI: розпорядник
    (фізична особа — власник порталу, ФОП не потрібен за ст. 4 Закону),
    які дані й навіщо збираються, правові підстави, треті особи
    (LiqPay, хостинг-провайдер), строк зберігання, права суб'єкта
    даних. Посилання — у футері `Site.master`.
  - Права суб'єкта персональних даних (доступ/виправлення/видалення/
    відкликання згоди) на цьому етапі реалізовано **лише «за запитом»
    на email розпорядника** — свідоме рішення користувача, окремого
    самообслуговування (сторінки профілю з видаленням акаунта) поки
    немає.
  - `RegisterConsumer.aspx`/`RegisterProvider.aspx` — доданий
    обов'язковий `chkPrivacyConsent` (CheckBox з посиланням на
    політику, відкривається в новій вкладці). **CheckBox не
    покривається `RequiredFieldValidator`** (той не працює для
    «має бути позначено») — перевірка вручну на сервері
    (`If Not chkPrivacyConsent.Checked Then ShowError(...)`), той
    самий прийом, що вже використовується для полів юрособи в
    `RegisterProvider.aspx.vb`.
  - Перевірено живим end-to-end тестуванням (PowerShell
    `Invoke-WebRequest`, той самий підхід, що curl): GET
    `PrivacyPolicy.aspx` → 200, кирилиця не побита, контакт
    розпорядника і посилання у футері на місці; POST реєстрації без
    згоди → форма коректно відхиляється з повідомленням «Підтвердьте
    згоду…», акаунт не створюється; POST зі згодою (Consumer і
    Provider) → реєстрація проходить штатно, як і до зміни.

## ⚠️ Граблі, на які вже наступили (щоб не повторювати)

1. **`CodeFile=`, а не `CodeBehind=`** у директивах `<%@ Page/Master/
   Application %>`. `CodeBehind` — атрибут для Web Application Project
   (VS компілює наперед у `bin/`); у файловій Website-моделі без нього
   ASP.NET просто не компілює код позаду розмітки і падає з
   `Could not load type` на першому ж запиті.
2. **Кирилиця з `<globalization>`** — без явних
   `fileEncoding="utf-8" requestEncoding="utf-8" responseEncoding="utf-8"`
   українські тексти на сторінці виходять побитими (подвійне
   перекодування UTF-8 ↔ Windows-1252).
3. **Ім'я змінної VB.NET не повинно збігатися з іменем типу без урахування
   регістру** — `Dim accountType = ...` поруч з `Enum AccountType` дає
   `BC30980`. VB.NET регістронезалежний, на відміну від C#.
4. **`ValidationSettings:UnobtrusiveValidationMode`** за замовчуванням у
   .NET 4.5+ вимагає ScriptResourceMapping для jQuery, якого в проєкті
   немає. Без `<add key="ValidationSettings:UnobtrusiveValidationMode"
   value="None" />` в `appSettings` будь-яка сторінка з
   `asp:*Validator` падає з 500 `InvalidOperationException`.
5. **AutoPostBack-послідовність не можна імітувати одним POST-ом** —
   при ручному тестуванні (curl/Postman) зміна `RadioButtonList`/
   `CheckBox` з `AutoPostBack="true"` в одному запиті разом з фінальним
   сабмітом ламає `EnableEventValidation` (`Invalid postback or callback
   argument`). Треба відтворювати кроки як реальний браузер: окремий
   POST на кожен `__EVENTTARGET`, з актуальним ViewState з попередньої
   відповіді.
6. **`Dim service`/`Dim accountType` — той самий регістронезалежний
   конфлікт з п.3, стався ще раз** у `ServiceEdit.aspx.vb` (клас
   `Service`). Локальна змінна перейменована на `svc`. Варто одразу
   уникати імен змінних, що збігаються (без урахування регістру) з
   будь-яким класом/enum у `App_Code`.
7. **`asp:LinkButton` не має атрибута `name=`** у рендері (це `<a
   href="javascript:__doPostBack(...)">`, а не `<input>`) — при
   ручному тестуванні POST-цілі шукати через
   `grep "__doPostBack\('[^']*'"`, а не через `name=`; аргументи в
   атрибуті `href` HTML-екрановані (`&#39;`, не `'`). Якщо на сторінці
   є хоч один валідатор, ASP.NET рендерить замість простого
   `__doPostBack` довшу форму —
   `WebForm_DoPostBackWithOptions(new WebForm_PostBackOptions(&quot;...&quot;, ...))`
   — ціль постбека там усередині лапок `&quot;`, шукати вже інший патерн.
8. **App Pool за замовчуванням не має прав на запис** поза `inetpub` —
   для збереження фото в `Uploads/` довелося явно додати ACL
   (`IIS AppPool\SumyPortalPool`, Modify) на цю папку.
9. **Databinding-вираз виконується навіть у прихованому (`Visible="false"`)
   елементі** — `Visible` лише ховає рендер, сам вираз усе одно
   обчислюється під час `DataBind()`. `ResolveUrl(Nothing)` тому кидав
   `ArgumentNullException`, хоча `<asp:Image Visible="...">` мав би
   просто не показатись. Захищати вираз самим (`If(cond, "", ResolveUrl(...))`),
   а не покладатись на `Visible`.

## Секрети (рядок підключення)

`Web.config` посилається на `ConnectionStrings.config`
(`<connectionStrings configSource="ConnectionStrings.config" />`) — це
нативний механізм .NET, підхоплюється автоматично, без транформацій
Web.config, які на Website Project без VS все одно не працюють.

- `ConnectionStrings.config.example` — шаблон, у git.
- `ConnectionStrings.config` — реальні дані, у `.gitignore`, **на кожній
  машині (dev/хостинг) створюється окремо** копіюванням прикладу з
  правильними логіном/паролем.

Той самий прийом — для ключів LiqPay (донат-модуль, п.1), тільки через
`<appSettings file="LiqPay.config">` (домердж, а не повна заміна):
`LiqPay.config.example` — шаблон у git, `LiqPay.config` — реальні
`LiqPayPublicKey`/`LiqPayPrivateKey`, у `.gitignore`. **Файл
обов'язково має існувати** (хай навіть з плейсхолдер-значеннями) —
інакше `Web.config` не завантажиться (помилка конфігурації при
першому запиті).

## Локальне dev-середовище (ця машина)

- **IIS**: увімкнено (роль Web-Server + `IIS-ASPNET45`), сайт
  `SumyPortal` в окремому пулі `SumyPortalPool` (.NET CLR v4.0,
  Integrated), фізичний шлях — ця папка, порт **8090**
  (`http://localhost:8090`). Служба `W3SVC` — автозапуск, переживе
  перезавантаження.
- **MySQL**: MySQL Server 8.4.9 встановлено через `winget` (пакет
  `Oracle.MySQL`), запущено як служба Windows **`MySQL84`** (автозапуск,
  порт 3306, `bind-address=127.0.0.1`). Дані:
  `C:\ProgramData\MySQL\MySQL Server 8.4\Data`, конфіг: той самий шлях,
  `my.ini`.
  - `root` має пароль (не порожній) — див. власні нотатки поза
    репозиторієм, тут навмисно не дублюється.
  - Робочий обліковий запис застосунку: `sumy_portal_app`@`localhost`,
    повні права лише на БД `sumy_portal`.
  - **Гоча Windows/PowerShell**: не пайпити SQL-текст у `mysql.exe` через
    PowerShell-конвеєр (`Get-Content | mysql`) — PowerShell 5.1
    перекодує рядки через OEM-кодову сторінку і кирилиця б'ється.
    Застосовувати схему тільки байтовим редіректом через `cmd.exe`
    (`cmd /c "mysql ... < schema.sql"`) з `--default-character-set=utf8mb4`.
- **Visual Studio відсутня** на машині — редагування через VS Code,
  локальний запуск через IIS напряму (без IIS Express).

## Розгортання на бойовий хостинг

Скопіювати вміст цієї папки (`portal/`) у кореневу директорію сайту на
хостингу (`bin/MySql.Data.dll` вже включено — донабирати нічого не
треба), і на хостингу:

- створити `ConnectionStrings.config` за зразком `.example` з реальними
  даними MySQL хостингу;
- створити `LiqPay.config` за зразком `.example` з реальними ключами з
  кабінету LiqPay (без нього сайт не запуститься — файл обов'язковий,
  навіть якщо донат-модуль поки не використовується);
- застосувати `App_Data/schema.sql` до бойової БД (або
  `migration_004_donations.sql` окремо, якщо схема вже розгорнута
  раніше без цієї таблиці);
- перевірити, що версія .NET Framework на хостингу ≥ 4.6.2 (потрібно
  для `MySql.Data.dll`) — 4.8 задекларовано в `Web.config`.
